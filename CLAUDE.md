# Ruhratna AI Stylist — Resume Context

This file is a snapshot for picking up the project in a fresh Claude thread. It captures product context, technical decisions, what is and isn't built, and the immediate next steps.

## Product context

- **Brand:** Ruhratna — a D2C imitation jewellery brand. Storefront at [ruhratna.com](https://ruhratna.com).
- **Stack:** WordPress + WooCommerce hosted on Kinsta.
- **This feature:** AI Stylist — the customer uploads an outfit photo, picks an occasion, and gets jewellery recommendations from the Ruhratna catalog. Surfaces on a dedicated page (planned: `ruhratna.com/ai-stylist`).

## Technical decisions made

- **Two separate API endpoints**, not one. `/analyse` (image → outfit JSON) returns in ~6s and lets the frontend show a "stylist reading" while `/match` (outfit JSON + catalog → recommendations) runs.
- **Model choice and fallback:**
  - `analyse.py` — primary `gemini-2.5-flash-lite`, fallback `gemini-3.1-flash-lite` (both Gemini — vision-categorical task, flash-lite is fast and reliable here).
  - `match.py` — primary `claude-sonnet-4-6` (Anthropic), fallback `gemini-2.5-flash-lite` (Gemini). **Cross-vendor fallback** — if Anthropic has an incident, Gemini Flash-lite keeps the recommendation flow alive. Pro (`gemini-2.5-pro`) was retired as primary in 2026-06 after observed latency tails of 30s–17min in production — the median was acceptable but the variance made it unsuitable for a customer-facing 50–60s SLA. Claude Sonnet has tighter tails and very strict JSON output discipline. Routing happens in `_call_model()` by model-name prefix (`claude-*` → Anthropic SDK, `gemini-*` → google-genai SDK).
  - The legacy Gemini-only call is **kept commented inside `match_jewellery`** as a rollback reference — to revert, swap `MATCH_MODEL_PRIMARY` back to `gemini-2.5-pro` and uncomment that block.
  - Both files use the same retry pattern: 3 attempts × 3-second sleep on the primary, then 3 attempts on the fallback, then return `{"error": "All models failed"}`. Implemented as a Python `for-else` over `[primary, fallback]` with an inner retry loop. (Worth tightening to single-attempt + per-call timeout — see the retry-strategy discussion in commits around this change.)
- **Catalog handling:** ~160+ products parsed from the live Ruhratna WooCommerce feed at `https://ruhratna.com/wp-content/uploads/woo-feed/chatgpt/xml/recommendationeng.xml` into two prepared artifacts — `catalog_products.json` (lookup dict for URL cross-referencing) and `catalog_formatted.txt` (the LLM-ready block embedded in the match prompt). `match.py` preloads both at module import time via `preload_catalog()` so the first request isn't slow.
- **Catalog auto-refresh.** `catalog.py`'s `SOURCE_PATH` now points at the live WooCommerce feed URL. On every Railway deploy the Procfile runs `python catalog.py` as a **pre-start** command before gunicorn boots — it fetches the feed, rewrites `catalog_products.json` / `catalog_formatted.txt` on disk, then exits. Gunicorn starts, `app.py` imports, and the existing module-level `preload_catalog()` reads the freshly-written files. No more in-process startup-refresh block. The pre-start uses `;` (not `&&`), so if the catalog fetch fails the exit code is ignored and gunicorn still boots, falling back to whatever JSON/TXT is on disk (the committed artifacts on a fresh deploy, the last successful refresh otherwise). A `POST /refresh-catalog` endpoint does refresh + `preload_catalog(force=True)` on demand — Railway cron hits this for periodic refreshes between deploys. **There is no background refresh thread** — earlier in this stack we had one, then realised that with multiple workers it only updates the worker that happens to run it; the cron-driven endpoint is simpler and more predictable.
- **Output structure** from `/match`: 3–6 recommendations split into tier 1 (top 3) and tier 2 (next 2–3, optional), classified by `type` (neck / ears / accent / hands), plus an optional `complete_look` block that only sets `suggested: true` when 2+ tier-1 picks of different types genuinely coordinate.
- **Image-quality gate on `/analyse`.** The analyse prompt asks Gemini to return `confidence_flag` (integer `0` or `1`) and `rejection_reason` (warm one-liner, ≤20 words; `""` when the flag is `1`). Gemini sets `0` for unusable inputs — no clothing visible, multiple people, headshot only, too blurry/dark, screenshot/illustration/cartoon, or clothing too partial to recommend against. When `/analyse` sees `confidence_flag == 0` it returns HTTP **200** with `{ success: false, error: true, confidence_flag: 0, rejection_reason, session_id, outfit_analysis: null }` — so the frontend must branch on the response body, not the status code. Rejected sessions are still logged (Stage 1 runs regardless). `app.py` defaults a missing flag to `1` (fail-open) so a malformed model response doesn't block the flow; hard failures (image decode, all models failed, parse error) are still a separate HTTP 400 path.
- **`temperature=0`** on every Gemini call for consistency between runs.
- **`v1alpha`** API version explicitly set on the genai client (`http_options={"api_version": "v1alpha"}`) — required to access the newer model IDs.
- **URL cross-reference:** after Gemini returns recommendations, `match.py` overwrites `image_url` and `product_url` from `catalog_products.json` keyed on `product_id`. So even if the model paraphrases or hallucinates a URL, the response carries the authoritative `ruhratna.com` link.
- **Async polling for `/match`**, not synchronous. **Status: DONE — live on Railway and working end-to-end.** `POST /match` generates a UUID `job_id`, spawns a background thread that runs `match_jewellery`, and returns `{"job_id": "..."}` with `202 Accepted` immediately. The client then polls `GET /result/<job_id>` until status is `done` or `error`. Avoids hitting reverse-proxy/CDN timeouts on the ~19s Gemini call and keeps the request worker free to serve other traffic while the Gemini round trip is in flight. Jobs live in an in-memory dict (`jobs`) guarded by a `threading.Lock`; the `/result` endpoint deletes the entry on the fetch that returns the final outcome (no TTL — jobs persist until claimed, lost on worker restart). In production we run the gunicorn `gevent` worker class, which monkey-patches `threading`, so `threading.Thread` becomes a cooperative greenlet and `match_jewellery`'s `requests`-based Gemini call yields the event loop on I/O.
- **Two-stage fire-and-forget session logging.** Logging is split across the two endpoints so the image upload happens at analyse-time (when the image is in hand) rather than being plumbed through `/match`. Each stage runs in its own `daemon=True` thread and returns immediately; the user response is never blocked, the worker can shut down without waiting, and all exceptions inside the `_do_log_*` workers are caught via `log.exception(...)` — nothing escapes.
  - **Stage 1 — `/analyse` → `log_analyse_session(...)`**: `/analyse` mints a `session_id = uuid.uuid4()` at the top of the handler, runs `analyse_outfit`, and calls `log_analyse_session` with the image, occasion, outfit JSON, analyse model, analyse time, and confidence flag — for **both** usable and rejected images. The thread uploads the image to **imgbb** (`_upload_to_imgbb` — a single `requests.post` with the base64 string; returns `""` on any failure, never raises), ensures the `Sessions` header row exists, and appends an 8-element row populating columns **A–H** (Session ID, Timestamp UTC, Occasion, Analyse Model, Analyse Time, Confidence Flag, Outfit Analysis JSON, Image URL). Columns I–N are intentionally left blank. The response body includes `session_id` so the frontend can pass it to `/match`.
  - **Stage 2 — `/match` → `log_match_session(...)`**: `/match` accepts an optional `session_id` field in the POST body, passes it to `_run_match`. After `match_jewellery` succeeds and the job is marked `done`, `_run_match` calls `log_match_session(session_id, match_result, match_model, match_time)`. The thread reads column A of the `Sessions` tab via `values.get`, finds the row index for `session_id`, and issues a `values.update` on the range `I{row}:N{row}` — populating Match Model, Match Time, Num Recommendations, Complete Look Suggested, Stylist Reading (first 200 chars), Recommendations JSON. If `session_id` isn't found, it emits `log.warning("session_id ... not found")` and returns.
  - **Soft race:** both stage-1 and stage-2 writes are async. If `/match` is hit immediately after `/analyse` returns, the stage-1 append may not have flushed yet, and stage 2 will warn "not found". In practice match takes ~19s while the stage-1 Sheets append is sub-second, so this rarely fires. If it ever shows up frequently in logs, add a small retry-with-backoff inside `_do_log_match`. Not added speculatively.
- **Logger transport: imgbb image + 14-column Sheets row, split across two writes.** Column layout is analyse-side first (A–H), match-side after (I–N) — see `HEADER_ROW` in [logger.py](logger.py) for the canonical order. **Images go to imgbb, not Google Drive.** A service account on a consumer Gmail has **0 Drive storage quota** — files it creates fail with `storageQuotaExceeded` even inside a folder shared with it as Editor, because the parent folder does not determine file ownership (the creating identity does, and it is billed for storage). imgbb sidesteps this entirely: `_upload_to_imgbb` POSTs the base64 to `api.imgbb.com/1/upload` with `IMGBB_API_KEY` and returns a public direct URL. Sheets auth is still a service account; the full JSON lives in env var `GOOGLE_SERVICE_ACCOUNT_JSON` (one-line string), parsed with `json.loads` at log time. Scope: `spreadsheets` only (the `drive.file` scope was dropped). The target Sheet must be shared with the service account's `client_email` as Editor.
- **`session_id` is the join key, not `job_id`.** `session_id` is generated at `/analyse` time and travels through the frontend back to `/match`; the row on the Sheet is keyed on it. `job_id` is purely the in-memory polling handle for the `/match` async pattern — never written to the Sheet. Don't conflate them.
- **Timing is measured locally at each stage.** `/analyse` times `analyse_outfit` and passes `analyse_elapsed` directly to `log_analyse_session`; `_run_match` times `match_jewellery` and passes it to `log_match_session`. The `outfit_analysis._analyse_time` field is still set as a convenience for the frontend, but is no longer load-bearing for logging.

## What is built

- **`catalog.py`** — feed parser. Reads the live XML feed from `ruhratna.com`, filters out `Gift Cards`, `Hot Pick Any 5 @ 1999`, `Combo`, and out-of-stock items. Writes `catalog_products.json` and `catalog_formatted.txt`. Run as a Procfile pre-start command on every deploy (`python catalog.py ; gunicorn ...`) and on demand by `POST /refresh-catalog` (which calls `main` in-process via `from catalog import main as refresh_catalog`). Still runnable standalone as `python catalog.py`.
- **`analyse.py`** — Call 1. Takes `(image_base64, occasion)`, returns the structured outfit dict. Has a CLI test block: `python analyse.py img.jpg office`.
- **`match.py`** — Call 2. Takes `(outfit_analysis, occasion)`, returns `{stylist_reading, recommendations, complete_look}`. Cross-references URLs. Has a CLI test block with a hardcoded black-saree sample.
- **`app.py`** — Flask REST API. `POST /analyse` (sync, ~6s blocking) returns `{ success, session_id, outfit_analysis }` on a usable image, or the rejection shape `{ success: false, error: true, confidence_flag: 0, rejection_reason, session_id, outfit_analysis: null }` when Gemini flags the image — **both at HTTP 200**. `GET /health` is a normal blocking endpoint. `POST /match` is asynchronous: it accepts an optional `session_id`, queues a job, and returns a `job_id`. `GET /result/<job_id>` polls the job state and returns `running` / `done` / `error`. Done and errored jobs are deleted on fetch. `POST /refresh-catalog` triggers a feed re-fetch + `preload_catalog(force=True)` and returns `{ success }`. CORS enabled for all origins. On import, `preload_catalog()` runs once at module level — it picks up whatever files the Procfile pre-start (`python catalog.py`) wrote moments earlier.
- **`logger.py`** — two-stage fire-and-forget session logger. Public surface is two functions: `log_analyse_session(...)` (imgbb upload + new row populating A–H) and `log_match_session(...)` (in-place update of I–N keyed on `session_id`). Each spawns its own `daemon=True` thread and returns immediately. Internal `_do_log_analyse` / `_do_log_match` workers wrap their work in `try/except → log.exception(...)`; nothing escapes. The 14-column `HEADER_ROW` constant is the canonical column order.
- **Deployment plumbing** — `Procfile` (gunicorn + gevent worker class, **1 worker** × 100 connections, 120s timeout, plus `--log-level info --capture-output --enable-stdio-inheritance` so daemon-thread logging reaches Railway), `runtime.txt` (Python 3.11.12), `.railwayignore`, `gevent` + `gunicorn` + `google-api-python-client` + `google-auth` + `requests` in `requirements.txt`.
- **Live on Railway** — **DONE.** Deployed from this repo on the `main` branch. Live URL: <https://web-production-8b1fc.up.railway.app>. Env vars set in the Railway dashboard.

## Performance (measured locally)

- `/analyse` → ~6 seconds end-to-end
- `/match` → ~19 seconds (heavier prompt, larger output, `gemini-2.5-pro`)
- User-facing flow: outfit reading appears at ~6s, recommendations at ~25s total

The 120-second gunicorn timeout in `Procfile` accommodates this with generous headroom. The user-facing wait is also gated by the WordPress plugin's polling interval (~2s), so a typical end-to-end `/match` round trip is ~21–22s wall-clock.

## Railway deployment setup

Railway uses its default Nixpacks builder — there's no `railway.json` or `nixpacks.toml`. It just picks up the files in the repo root and builds.

- **`ai-stylist-backend/` IS the repo root.** No monorepo subdir config needed on the Railway side.
- **`Procfile`** — `web: python catalog.py ; gunicorn app:app --worker-class gevent --workers 1 --worker-connections 100 --timeout 120 --log-level info --capture-output --enable-stdio-inheritance --bind 0.0.0.0:$PORT`. **Pre-start:** `python catalog.py` runs to completion (or failure) before gunicorn ever starts, so when the worker boots and `app.py` calls `preload_catalog()` it reads a fresh JSON/TXT pair. **`;` not `&&`:** if the feed fetch fails the exit code is ignored and gunicorn boots anyway, falling back to the JSON/TXT already on disk. **Gunicorn:** one `gevent` worker × 100 cooperative greenlet connections (~100 concurrent in-flight requests). 120s worker timeout protects against a stuck Gemini call. `gevent` monkey-patches `threading`, which is what makes the background-thread polling pattern in `app.py` actually cooperative under load (greenlets that yield on I/O) rather than spawning real OS threads. **Why single-worker:** `/refresh-catalog` mutates the module-level cache in the worker that handles the request; with multiple workers, only that one worker would see the fresh catalog while others kept serving stale data. Going to `--workers 1` makes the cache state singular and the refresh deterministic. **Why the three log flags:** `--capture-output --enable-stdio-inheritance` ensure stdlib-`logging` output from every module — including the daemon threads `log_analyse_session`/`log_match_session` spawn — is captured by gunicorn and forwarded to Railway's log stream instead of being swallowed by gevent's stdio buffering. They are **required**, not optional. `--log-level info` sets gunicorn's own log verbosity. `--preload` is deliberately not used: with a single worker there's no fork-duplication problem for it to solve.
- **`runtime.txt`** — `python-3.11.12`. Started at `python-3.11.0` but Railway's Nixpacks didn't resolve that exact patch, so it was bumped to 3.11.9. Bumped again to 3.11.12 in 2026-06 after Railway's `mise` package manager upgraded to 2026.6.1 and started requiring GitHub artifact attestations for every Python install — 3.11.9 predates those attestations and the build started failing with `mise ERROR Failed to install core:python@3.11.9: No GitHub artifact attestations`. Don't downgrade without re-testing the build. Alternative workaround (not used): set `MISE_PYTHON_GITHUB_ATTESTATIONS=false` as a Railway env var to skip the check.
- **`.railwayignore`** — excludes `.env`, `__pycache__/`, `*.pyc`, `venv/`, images (`*.jpeg` / `*.jpg` / `*.png`), and `*.xml` so the source product feed and local test images stay out of the build context. Mirrors `.gitignore` roughly but isn't a substitute for it — both files exist independently.
- **Env vars are set in the Railway dashboard, not via `.env`.** The dashboard is the source of truth in production; `.env` is local-dev only and excluded from both git and the Railway build context. The keys to set: `GEMINI_API_KEY`, `ANTHROPIC_API_KEY`, `ANALYSE_MODEL_PRIMARY`, `ANALYSE_MODEL_FALLBACK`, `MATCH_MODEL_PRIMARY` (now `claude-sonnet-4-6`), `MATCH_MODEL_FALLBACK`, and the three logger keys `GOOGLE_SERVICE_ACCOUNT_JSON` (full service-account JSON as a single-line string), `SHEETS_ID`, `IMGBB_API_KEY`. `PORT` is injected automatically by Railway and read by the Procfile's `$PORT`. The target Sheet must be shared with the service account's `client_email` as Editor — otherwise the append/update will 403 and the logger logs a warning per session (the user flow is unaffected). A missing or invalid `IMGBB_API_KEY` just leaves the Image URL column empty; the rest of logging proceeds. (`DRIVE_FOLDER_ID` was removed when the image upload moved from Google Drive to imgbb.)
- **CORS** is permissive (`CORS(app)` in `app.py`, no origin allowlist) so the WordPress plugin can call from any origin once deployed. Tighten later if needed.
- **Catalog artifacts ship in the repo as a fallback only.** `catalog/catalog_products.json` and `catalog/catalog_formatted.txt` are committed and travel to Railway via the build context, but they're only used as the fallback when the live feed fetch fails on cold start. The `.gitignore` lists both paths so locally regenerated copies don't accidentally get re-committed via `git add .` — but already-tracked files still appear in `git status` when modified (a quirk of how `.gitignore` works). On every deploy the app pulls a fresh feed from `ruhratna.com` and overwrites these files; between deploys, hit `POST /refresh-catalog` (typically via Railway cron) to refresh in-place. The source XML stays gitignored / railwayignored — only the parsed artifacts and the catalog code travel with deploys.

## Conventions worth knowing

- **Prompts use `__SENTINEL__` placeholders + `.replace()`**, not f-strings. The prompts contain literal `{` `}` JSON braces that would break f-string parsing.
- **JSON parsing uses `removeprefix`/`removesuffix`**, not `.strip("```json")`. The latter is a Python footgun (strips characters from a set, not a substring).
- **Each module reads its own env vars at import time** via `python-dotenv`. No central config object.
- **`match.py` preloads the catalog via a module-level cache** (`_catalog_text`, `_product_lookup`). `match_jewellery()` calls `preload_catalog()` defensively, so standalone `python match.py` runs work too.
- **The `for-else` pattern in retry/fallback logic is intentional.** The inner loop's `break` happens only on success; on retry exhaustion, the loop completes naturally so the `for-else` triggers `continue` to the next model.
- **All modules use stdlib `logging`, never `print()`.** Each file does `log = logging.getLogger(__name__)`; `app.py` calls `logging.basicConfig(level=INFO, ..., force=True)` once at import time (before the local imports) so worker output is configured before `preload_catalog()` and the logger threads ever emit. CLI test blocks in `analyse.py` / `match.py` / `catalog.py` call `basicConfig` themselves so standalone runs still print. Diagnostic messages use `%`-style lazy formatting (`log.info("x=%s", x)`), and `except` blocks use `log.exception(...)` to capture the traceback.
